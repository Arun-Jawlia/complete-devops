# Docker Logs, Exec, Inspect & Networks

These four commands are especially important when you move from basic Docker usage to **debugging and managing real applications**.

A useful mental model:

```text
                    Docker
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
     Container      Network       Image
        │
   ┌────┼────┐
   ↓    ↓    ↓
 logs  exec inspect
```

---

# 1. `docker logs`

## What is `docker logs`?

`docker logs` displays the **logs generated by a container's main process**.

If your application is running inside a container and something goes wrong, logs are usually the first place you check.

### Syntax

```bash
docker logs CONTAINER
```

Example:

```bash
docker logs my-nginx
```

---

## Example

Start a container:

```bash
docker run -d --name my-nginx nginx
```

Then:

```bash
docker logs my-nginx
```

You may see messages generated by Nginx.

If you access:

```text
http://localhost:8080
```

and your Nginx container is configured to log requests, those requests can appear in the container logs.

---

## Follow logs in real time

One of the most useful options is:

```bash
docker logs -f my-nginx
```

`-f` means **follow**.

It is similar to:

```bash
tail -f
```

in Linux.

The terminal stays attached to the log stream:

```text
Request 1
Request 2
Request 3
Request 4
...
```

Press:

```text
Ctrl + C
```

to stop following the logs.

**This does not stop the container.**

---

## Show only recent logs

```bash
docker logs --tail 50 my-nginx
```

This shows the last 50 lines.

You can also combine it with `-f`:

```bash
docker logs -f --tail 50 my-nginx
```

Meaning:

> Show the last 50 lines and continue following new logs.

---

## Show timestamps

```bash
docker logs -t my-nginx
```

Example:

```text
2026-08-19T10:20:30.123Z Request received
2026-08-19T10:20:35.456Z Request completed
```

---

## When do you use `docker logs`?

Suppose your Flask application is running:

```bash
docker run -d --name flask-app flask-image
```

The application isn't working.

First:

```bash
docker ps
```

Then:

```bash
docker logs flask-app
```

You might discover:

```text
ModuleNotFoundError: No module named 'pymongo'
```

So instead of guessing, you can identify the actual application error.

### Common debugging command

```bash
docker logs -f --tail 100 flask-app
```

---

# 2. `docker exec`

## What is `docker exec`?

`docker exec` allows you to **execute a command inside an already running container**.

This is extremely useful for debugging.

### Syntax

```bash
docker exec CONTAINER COMMAND
```

Example:

```bash
docker exec my-nginx ls
```

This executes:

```bash
ls
```

inside the container.

---

# Open a shell inside a container

The most common usage is:

```bash
docker exec -it my-nginx bash
```

Here:

| Option | Meaning                      |
| ------ | ---------------------------- |
| `exec` | Execute command in container |
| `-i`   | Interactive                  |
| `-t`   | Allocate terminal            |
| `bash` | Start Bash shell             |

You will get something like:

```text
root@abc123:/#
```

Now you are **inside the container**.

You can run:

```bash
ls
```

```bash
pwd
```

```bash
cd /etc
```

```bash
ls nginx
```

---

## What if Bash doesn't exist?

Many lightweight Docker images don't include Bash.

For example, Alpine-based images commonly use `sh`.

Then use:

```bash
docker exec -it my-container sh
```

So:

```text
Ubuntu/Debian-based image → bash
Alpine-based image        → sh
```

---

## Execute a specific command

You don't have to open a shell.

For example:

```bash
docker exec my-nginx nginx -v
```

Or:

```bash
docker exec my-nginx ls /etc/nginx
```

Or:

```bash
docker exec my-nginx cat /etc/nginx/nginx.conf
```

---

## Why is `docker exec` useful?

Imagine your application container is behaving strangely.

You can enter it:

```bash
docker exec -it my-app bash
```

Then inspect:

```bash
ls
```

```bash
env
```

```bash
ps
```

```bash
cat config.json
```

You can investigate the container's environment directly.

---

# 3. `docker inspect`

## What is `docker inspect`?

`docker inspect` displays **detailed low-level information about Docker objects**.

You can inspect:

* Containers
* Images
* Networks
* Volumes

For a container:

```bash
docker inspect my-nginx
```

The output is usually a large JSON object.

---

## Why do we need it?

`docker ps` gives you a **summary**.

```bash
docker ps
```

might show:

```text
CONTAINER ID   IMAGE   STATUS
abc123         nginx   Up 5 minutes
```

But `docker inspect` gives you detailed configuration.

For example:

```text
Container ID
Image
Created time
Environment variables
Mounts
Networks
IP address
Port configuration
Restart policy
Command
Entrypoint
```

---

# Example

```bash
docker inspect my-nginx
```

You may find:

```json
{
  "Id": "abc123...",
  "Name": "/my-nginx",
  "State": {
    "Status": "running"
  },
  "Config": {
    "Image": "nginx"
  },
  "NetworkSettings": {
    "IPAddress": "172.17.0.2"
  }
}
```

The actual output is much larger.

---

# Get a specific value

Because `docker inspect` returns JSON, you can use Go templates to extract specific information.

For example:

```bash
docker inspect -f '{{.NetworkSettings.IPAddress}}' my-nginx
```

This gives the container's IP address.

Example:

```text
172.17.0.2
```

Another useful example:

```bash
docker inspect -f '{{.State.Status}}' my-nginx
```

Output:

```text
running
```

---

## `docker inspect` vs `docker ps`

Think of it this way:

```text
docker ps
     ↓
High-level information
     ↓
"What containers are running?"
```

while:

```text
docker inspect
     ↓
Detailed configuration
     ↓
"Exactly how is this container configured?"
```

# 4. Docker Networks

Now we move to an extremely important Docker concept.

Suppose you have:

```text
Frontend
   ↓
Backend
   ↓
MongoDB
```

Each application could run in its own container:

```text
┌───────────────┐
│ Frontend      │
│ Container     │
└───────┬───────┘
        │
        ↓
┌───────────────┐
│ Backend       │
│ Container     │
└───────┬───────┘
        │
        ↓
┌───────────────┐
│ MongoDB       │
│ Container     │
└───────────────┘
```

How do these containers communicate?

**Docker networks.**

---

# What is a Docker Network?

A Docker network provides a mechanism for **communication between containers**.

For example:

```text
                    Docker Network
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
      Frontend        Backend        MongoDB
      Container       Container      Container
```

Containers connected to the same Docker network can communicate with each other.

---

# List Docker Networks

Use:

```bash
docker network ls
```

Example:

```text
NETWORK ID     NAME      DRIVER    SCOPE
abc123         bridge    bridge    local
def456         host      host      local
ghi789         none      null      local
```

Docker provides several built-in network types.

The most important for beginners is:

```text
bridge
```

---

# Create a Docker Network

Syntax:

```bash
docker network create NETWORK_NAME
```

Example:

```bash
docker network create my-network
```

Check:

```bash
docker network ls
```

You should see:

```text
my-network
```

---

# Run containers on a network

Suppose we want a backend and MongoDB.

Create the network:

```bash
docker network create my-network
```

Run MongoDB:

```bash
docker run -d \
  --name mongodb \
  --network my-network \
  mongo
```

Run backend:

```bash
docker run -d \
  --name backend \
  --network my-network \
  backend-image
```

Now:

```text
              my-network
                  │
         ┌────────┴────────┐
         ↓                 ↓
     backend             mongodb
```

The backend can communicate with MongoDB through the container name:

```text
mongodb
```

For example, your application might use:

```text
mongodb://mongodb:27017/mydatabase
```

This is a major Docker concept.

---

# Why use container names?

Without Docker networking, beginners often try to use:

```text
localhost
```

inside the backend container:

```text
mongodb://localhost:27017
```

That is usually wrong.

Why?

Because inside the backend container:

```text
localhost
```

means:

> **the backend container itself**

It does **not** mean the MongoDB container.

Instead:

```text
backend container
      │
      │ Docker network
      ↓
mongodb container
```

Use:

```text
mongodb://mongodb:27017
```

where `mongodb` is the MongoDB container's name.

---

# Inspect a Network

Use:

```bash
docker network inspect my-network
```

You can see information such as:

* Network driver
* Subnet
* Gateway
* Connected containers
* Container IP addresses

For example:

```text
my-network
    │
    ├── backend
    │      IP: 172.18.0.2
    │
    └── mongodb
           IP: 172.18.0.3
```

---

# Connect an Existing Container to a Network

Suppose the container already exists:

```bash
docker run -d --name backend backend-image
```

You can connect it to a network:

```bash
docker network connect my-network backend
```

Now:

```text
backend
   │
   └── connected to my-network
```

---

# Disconnect a Container

```bash
docker network disconnect my-network backend
```

---

# Remove a Network

```bash
docker network rm my-network
```

The network generally needs to have no connected containers before it can be removed.

---

# Complete Example: Backend + MongoDB

Let's put everything together.

### 1. Create network

```bash
docker network create app-network
```

### 2. Start MongoDB

```bash
docker run -d \
  --name mongodb \
  --network app-network \
  mongo
```

### 3. Start backend

```bash
docker run -d \
  --name backend \
  --network app-network \
  backend-image
```

Architecture:

```text
                    app-network
                         │
             ┌───────────┴───────────┐
             │                       │
             ↓                       ↓
       ┌───────────┐           ┌───────────┐
       │  Backend  │ ────────→ │  MongoDB  │
       │ Container │           │ Container │
       └───────────┘           └───────────┘
```

Backend connection string:

```text
mongodb://mongodb:27017/mydatabase
```

Notice:

```text
mongodb
```

is the **container name**, not an IP address.

# `docker logs` vs `docker exec` vs `docker inspect`

These three commands are easy to confuse.

| Command          | Purpose                            | Example                        |
| ---------------- | ---------------------------------- | ------------------------------ |
| `docker logs`    | See application/container logs     | `docker logs backend`          |
| `docker exec`    | Run commands inside container      | `docker exec -it backend bash` |
| `docker inspect` | View detailed Docker configuration | `docker inspect backend`       |

Think:

```text
Something is failing?
        │
        ├── docker logs
        │      ↓
        │   See errors
        │
        ├── docker exec
        │      ↓
        │   Enter/debug container
        │
        └── docker inspect
               ↓
          Check configuration
```

---

# Docker Network Commands to Remember

```bash
# List networks
docker network ls

# Create network
docker network create app-network

# Inspect network
docker network inspect app-network

# Connect container
docker network connect app-network backend

# Disconnect container
docker network disconnect app-network backend

# Remove network
docker network rm app-network
```

## The key concept

For a typical Dockerized application:

```text
                    Docker
                      │
                app-network
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
     Frontend       Backend       MongoDB
     :3000          :5000          :27017
        │             │             │
        └─────────────┴─────────────┘
                  Network
```

**Port mapping (`-p`) is primarily for communication between the host/external clients and a container. Docker networks are primarily for communication between containers.**

That distinction becomes very important when you start Dockerizing a **MERN application** or a **Python/Flask + MongoDB application**.
